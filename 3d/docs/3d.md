# eZ80-local integer 3D arithmetic

`3d.inc` provides integer arithmetic and transforms for values compatible with
the Pingo 3D VDU interface. This note records the numeric formats, register
conventions, and implementation strategy beside the code.

## Numeric domains

Pingo transports numeric arguments as little-endian 16-bit words. Their
interpretation depends on the command:

| Domain | Encoding | Decoding |
|---|---:|---:|
| Mesh coordinate | signed normalized | `raw / 32767` |
| Rotation angle | signed normalized turn | `raw * 2*pi / 32767` |
| Translation | signed normalized distance | `raw * 256 / 32767` |
| Scale | unsigned 8.8 | `raw / 256` |
| Texture coordinate | unsigned normalized | `raw / 65535` |

A local `vec3` is three consecutive 16-bit components and occupies six bytes.
The storage layout does not identify the numeric domain; the operation does.

## Logical register widths

General-purpose register pairs are treated as 16-bit values unless a routine
explicitly says otherwise. Their eZ80 upper bytes are normally irrelevant:

- logical `HL` means bytes `H:L`;
- logical `DE` means bytes `D:E`;
- logical `BC` means bytes `B:C`; and
- logical `HL:DE` is a 32-bit value in bytes `H:L:D:E`.

`UHL`, `UDE`, and `UBC` are ignored or deliberately zeroed. Pair arithmetic
that must be 16-bit uses the `.s` instruction suffix.

When a genuinely zero-extended register pair is required, the project-tested
undocumented idiom is:

```asm
    inc hl
    dec.s hl
```

The sequence preserves the low 16-bit value and clears `UHL`. The equivalent
sequence applies to the other register pairs. It changes flags and should not
be used when no following instruction observes the upper byte.

## Unsigned 16-by-16 multiplication

For operands:

```text
x = xh:xl
y = yh:yl
```

form four byte products with `mlt`:

```text
p00 = xl * yl
p10 = xh * yl
p01 = xl * yh
p11 = xh * yh
```

and combine them as:

```text
product = p00 + ((p10 + p01) << 8) + (p11 << 16)
```

The leaf routine uses only the active `AF`, `BC`, `DE`, and `HL` banks. It
does not use the stack, scratch memory, or `exx`, and it never needs to inspect
an upper register byte. Its public result is logical `HL:DE`.

Keeping the leaf routine out of the shadow bank is intentional: callers can
retain another complete operand set or 32-bit product in `BC'`, `DE'`, and
`HL'`.

## Signed multiplication

The signed wrapper:

1. XORs the operand sign bytes and parks the resulting flags in `AF'`.
2. Forms the absolute value of each 16-bit operand bytewise.
3. Calls the unsigned leaf routine.
4. Restores the sign flags with `ex af,af'`.
5. Negates logical `H:L:D:E` bytewise when the signs differed.

This naturally handles zero and `-32768`. It requires no data pushes, scratch
memory, or special zero unwind. It destroys both `AF` banks but preserves the
shadow general-purpose registers.

## Two-product accumulation

An axis rotation contains expressions such as:

```text
y' = (y*cos - z*sin) / 32767
z' = (y*sin + z*cos) / 32767
```

Both products are accumulated at full 32-bit width before narrowing. Rounding
each product separately would lose precision.

For one two-product expression, preload:

```text
active bank: HL = operand 0a, DE = operand 0b
shadow bank: HL = operand 1a, DE = operand 1b
```

Then:

```asm
    call p3d_smul16x16_32   ; active bank receives product 0
    exx                     ; park product 0 and expose operands 1a/1b
    call p3d_smul16x16_32   ; active bank receives product 1
```

The add/subtract primitives ferry product 1 through `A` one byte at a time,
using `exx` to reach product 0. `exx`, `ld`, and `cpl` preserve carry, allowing
ordinary `add`/`adc` or complemented `adc` chains across all four bytes.

The accumulator uses seven exchanges and returns with the opposite bank
active. Together with the exchange between the two multiplies, the complete
operation performs eight exchanges and therefore restores the outer caller's
original bank.

This bank-changing contract is for internal composed arithmetic. Callers must
not use `p3d_sadd32` or `p3d_ssub32` as conventional bank-preserving helpers
without accounting for the final active bank.

## Split-bank alternative

Some later multiply-accumulate code may benefit from the BBC floating-point
package's split representation:

```text
value 0 high word = HL
value 0 low word  = HL'
value 1 high word = DE
value 1 low word  = DE'
```

A 32-bit addition is then:

```asm
    exx
    add.s hl,de             ; low words
    exx
    adc.s hl,de             ; high words
```

`fpp.inc` uses this pattern in `ADD_`, `SUB_`, and `X2`. The initial 3D API
retains logical `HL:DE` at multiplication boundaries because it is easier to
call and test. A specialized dot-product primitive may use the split layout
internally when the conversion cost is recovered over several operations.

## Narrowing by 32767

Normalized multiplication and rotation require:

```text
result = round(product / 32767)
```

For a nonnegative 32-bit magnitude `n`, write:

```text
q = n >> 15
r = n & 32767
```

Because `32768 = 32767 + 1`:

```text
n = q*32767 + (q+r)
```

Only the small value `q+r` remains to be reduced. For inputs below `2^31`, it
is at most 17 bits and needs no more than three subtractions of 32767. The
remainder rounds upward when it is at least 16384. Since 32767 is odd, an
exact half-way tie cannot occur.

The implementation first rejects magnitudes above `0x3fffbfff`, the largest
one that can round to an allowed negative result. Under that guard, `q+r` is
at most 49150 and therefore needs at most one subtraction.

The signed routine divides the magnitude and reapplies the sign, which makes
its rounding rule nearest with magnitude increasing at the half boundary.
Carry reports a result outside signed 16-bit range.

## Rotation-intermediate bound

Generated sine and cosine coefficients must remain in:

```text
-32767 .. +32767
```

For a signed 16-bit vector component, the largest possible magnitude of a
two-product rotation intermediate is:

```text
2 * 32768 * 32767 = 2147418112
```

That is 65535 below signed 32-bit maximum, so a two-term rotation expression
cannot overflow its signed 32-bit intermediate. Emitting `-32768` as a trig
coefficient would remove that guarantee and is forbidden.

## Trigonometric lookup

The existing `sin168` table is not the final lookup for this layer. It stores
257 three-byte Q16.8 samples, truncates the incoming phase to a 1/256-turn
index, and has much less coefficient precision than a signed normalized
16-bit rotation needs.

`p3d_sincos16` uses a generated, interleaved 256-entry table:

```text
dw round(32767*sin(2*pi*i/256))
dw round(32767*cos(2*pi*i/256))
```

`scripts/generate_sincos_table.py` enforces exact cardinal values, symmetry,
and the coefficient range `-32767..32767`. Its packed 1,024-byte table has
SHA-256
`98a6464b9f25bd589351585972014e17e15b23f5f364d2a9d630e4205630d864`.

The exact nearest-bin mapping from every signed Pingo angle is:

```text
m = abs(raw)
n = (m + 64) >> 7
index = raw < 0 ? -n : n  (mod 256)
```

This maps `-32768` through the unsigned magnitude 32768. All table bins,
nearest-bin boundaries, signed endpoints, and 10,000 seeded random angles are
covered by the transform regression suite.

## Transform contracts

Translation performs three signed low-16 additions. It commits all three
components only when every addition is representable; carry leaves the input
vector unchanged.

Axis rotations match Pingo's current matrices:

```text
X: y' = round((y*cos - z*sin) / 32767)
   z' = round((y*sin + z*cos) / 32767)

Y: x' = round((x*cos + z*sin) / 32767)
   z' = round((z*cos - x*sin) / 32767)

Z: x' = round((x*cos - y*sin) / 32767)
   y' = round((x*sin + y*cos) / 32767)
```

Each two-product numerator is accumulated at signed 32-bit width and narrowed
once. Axis routines are transactional: carry leaves all three components
unchanged. XYZ rotation applies X, then Y, then Z and restores the original
vector if any axis fails.

`p3d_mat3_mul_vec3_16` consumes an 18-byte row-major matrix whose coefficients
are restricted to `-32767..32767`. Each row accumulates three products at
signed 32-bit width and narrows once. Carry reports either accumulator or
result overflow and leaves the input vector unchanged.

The axis and matrix routines deliberately use a small number of balanced stack
operations to retain in-place transactional behavior while the GP shadow bank
holds full-width products. IX and IY are preserved.

## Shadow-register and interrupt contract

Routines document both active- and shadow-bank destruction explicitly.
Code using `exx` or `ex af,af'` assumes any enabled interrupt handler preserves
the register banks it uses. If an application has a different interrupt
contract, it must protect the call at that integration boundary rather than
adding stack traffic to every arithmetic primitive.

## Validation status

The assembled routines pass two deterministic suites under the current
Pingo-compatible Fab profile:

- 60,596 scalar arithmetic records;
- 71,834 trigonometric and transform records.

Both suites contain at least 10,000 seeded random records per public operation
plus directed endpoints, rounding boundaries, cardinal rotations, signed
overflow, atomic-failure, dense matrix, and accumulator-overflow cases. PRT1
timing excludes file I/O and includes the same operand setup, comparison, and
loop bookkeeping convention used by the original AgonMaths fixtures.
The transform harness also verifies IX/IY preservation on every vector
operation, full 24-bit shadow-GP preservation where promised, and that no
operation writes into its 18-byte auxiliary input field.

The correctness-loop timing is useful for regression comparisons, but it is
not a full-success frame budget: its random workload includes operations that
take an early overflow exit. After a clean transform run, the harness therefore
performs a second, file-free benchmark of 20,000 guaranteed-success calls per
entry point. It uses invariant half-turn rotations and identity-like matrix
fixtures, measures matching empty loops, and subtracts the loop, `DI`/`EI`, and
angle-load baseline. The resulting times retain API `CALL`/`RET` and the entire
successful arithmetic path. Each raw interval is uninterrupted, leaving only
the PRT's sub-millisecond quantization and the corresponding baseline-
subtraction uncertainty.

Hardware execution remains a separate validation gate.
