# Pingo3D eZ80 API

`3d.inc` provides the Pingo3D integer arithmetic, transforms, retained state,
and packet construction used with the Pingo 3D VDU interface. This note
records the numeric formats, register conventions, and implementation
strategy beside the code. The established source filenames and `p3d_*` symbol
prefix remain part of the API.

## Numeric domains

Pingo transports numeric arguments as little-endian 16-bit words. Their
interpretation depends on the command:

| Domain | Encoding | Decoding |
|---|---:|---:|
| Mesh coordinate | signed normalized | `raw / 32767` |
| Rotation angle | signed normalized turn | `raw * 2*pi / 32767` |
| Translation | signed normalized distance | `raw * 256 / 32767` |
| Scale | unsigned 8.8 | `raw / 256` |
| Texture coordinate | unsigned normalized | `raw / 65535` |

A local `vec3` is three consecutive 16-bit components and occupies six bytes.
The storage layout does not identify the numeric domain; the operation does.

## Logical register widths

General-purpose register pairs are treated as 16-bit values unless a routine
explicitly says otherwise. Their eZ80 upper bytes are normally irrelevant:

- logical `HL` means bytes `H:L`;
- logical `DE` means bytes `D:E`;
- logical `BC` means bytes `B:C`; and
- logical `HL:DE` is a 32-bit value in bytes `H:L:D:E`.

`UHL`, `UDE`, and `UBC` are ignored or deliberately zeroed. Pair arithmetic
that must be 16-bit uses the `.s` instruction suffix.

This convention is not a ban on native ADL-width work. A routine whose
documented value is genuinely 24-bit may deliberately load or store all three
bytes of a register pair. A packed 32-bit value may, for example, be stored as
`ld (foo),hl` for its low three bytes followed by `ld (foo+3),a` for its high
byte. Likewise, keeping the fourth byte in `A` while carry propagates can be
the clearest local contract. Such uses must be explicit at the instruction or
routine boundary; they are not candidates for automatic bytewise rewriting.
The look-at solver's staged radicand and `p3d_lookat_isqrt24` are intentional
examples.

When a genuinely zero-extended register pair is required, the project-tested
undocumented idiom is:

```asm
    inc hl
    dec.s hl
```

The sequence preserves the low 16-bit value and clears `UHL`. The equivalent
sequence applies to the other register pairs. It changes flags and should not
be used when no following instruction observes the upper byte.

## Unsigned 16-by-16 multiplication

For operands:

```text
x = xh:xl
y = yh:yl
```

form four byte products with `mlt`:

```text
p00 = xl * yl
p10 = xh * yl
p01 = xl * yh
p11 = xh * yh
```

and combine them as:

```text
product = p00 + ((p10 + p01) << 8) + (p11 << 16)
```

The leaf routine uses only the active `AF`, `BC`, `DE`, and `HL` banks. It
does not use the stack, scratch memory, or `exx`, and it never needs to inspect
an upper register byte. Its public result is logical `HL:DE`.

Keeping the leaf routine out of the shadow bank is intentional: callers can
retain another complete operand set or 32-bit product in `BC'`, `DE'`, and
`HL'`.

## Signed multiplication

The signed wrapper:

1. XORs the operand sign bytes and parks the resulting flags in `AF'`.
2. Forms the absolute value of each 16-bit operand bytewise.
3. Calls the unsigned leaf routine.
4. Restores the sign flags with `ex af,af'`.
5. Negates logical `H:L:D:E` bytewise when the signs differed.

This naturally handles zero and `-32768`. It requires no data pushes, scratch
memory, or special zero unwind. It destroys both `AF` banks but preserves the
shadow general-purpose registers.

## Two-product accumulation

An axis rotation contains expressions such as:

```text
y' = (y*cos - z*sin) / 32767
z' = (y*sin + z*cos) / 32767
```

Both products are accumulated at full 32-bit width before narrowing. Rounding
each product separately would lose precision.

For one two-product expression, preload:

```text
active bank: HL = operand 0a, DE = operand 0b
shadow bank: HL = operand 1a, DE = operand 1b
```

Then:

```asm
    call p3d_smul16x16_32   ; active bank receives product 0
    exx                     ; park product 0 and expose operands 1a/1b
    call p3d_smul16x16_32   ; active bank receives product 1
```

The add/subtract primitives ferry product 1 through `A` one byte at a time,
using `exx` to reach product 0. `exx`, `ld`, and `cpl` preserve carry, allowing
ordinary `add`/`adc` or complemented `adc` chains across all four bytes.

The accumulator uses seven exchanges and returns with the opposite bank
active. Together with the exchange between the two multiplies, the complete
operation performs eight exchanges and therefore restores the outer caller's
original bank.

This bank-changing contract is for internal composed arithmetic. Callers must
not use `p3d_sadd32` or `p3d_ssub32` as conventional bank-preserving helpers
without accounting for the final active bank.

## Split-bank alternative

Some later multiply-accumulate code may benefit from the BBC floating-point
package's split representation:

```text
value 0 high word = HL
value 0 low word  = HL'
value 1 high word = DE
value 1 low word  = DE'
```

A 32-bit addition is then:

```asm
    exx
    add.s hl,de             ; low words
    exx
    adc.s hl,de             ; high words
```

`fpp.inc` uses this pattern in `ADD_`, `SUB_`, and `X2`. The Pingo3D API
retains logical `HL:DE` at multiplication boundaries because it is easier to
call and test. A specialized dot-product primitive may use the split layout
internally when the conversion cost is recovered over several operations.

## Narrowing by 32767

Normalized multiplication and rotation require:

```text
result = round(product / 32767)
```

For a nonnegative 32-bit magnitude `n`, write:

```text
q = n >> 15
r = n & 32767
```

Because `32768 = 32767 + 1`:

```text
n = q*32767 + (q+r)
```

Only the small value `q+r` remains to be reduced. For inputs below `2^31`, it
is at most 17 bits and needs no more than three subtractions of 32767. The
remainder rounds upward when it is at least 16384. Since 32767 is odd, an
exact half-way tie cannot occur.

The implementation first rejects magnitudes above `0x3fffbfff`, the largest
one that can round to an allowed negative result. Under that guard, `q+r` is
at most 49150 and therefore needs at most one subtraction.

The signed routine divides the magnitude and reapplies the sign, which makes
its rounding rule nearest with magnitude increasing at the half boundary.
Carry reports a result outside signed 16-bit range.

## Rotation-intermediate bound

Generated sine and cosine coefficients must remain in:

```text
-32767 .. +32767
```

For a signed 16-bit vector component, the largest possible magnitude of a
two-product rotation intermediate is:

```text
2 * 32768 * 32767 = 2147418112
```

That is 65535 below signed 32-bit maximum, so a two-term rotation expression
cannot overflow its signed 32-bit intermediate. Emitting `-32768` as a trig
coefficient would remove that guarantee and is forbidden.

## Trigonometric lookup

The existing `sin168` table is not the final lookup for this layer. It stores
257 three-byte Q16.8 samples, truncates the incoming phase to a 1/256-turn
index, and has much less coefficient precision than a signed normalized
16-bit rotation needs.

`p3d_sincos16` and `p3d_sincos_fine16` share a generated, interleaved
256-entry table:

```text
dw round(32767*sin(2*pi*i/256))
dw round(32767*cos(2*pi*i/256))
```

The include appends entry zero once as an interpolation sentinel.
`scripts/generate_sincos_table.py` enforces exact cardinal values, symmetry,
and the coefficient range `-32767..32767`. The sentinel is excluded from the
canonical packed 1,024-byte table SHA-256:
`98a6464b9f25bd589351585972014e17e15b23f5f364d2a9d630e4205630d864`.

The exact nearest-bin mapping from every signed Pingo angle is:

```text
m = abs(raw)
n = (m + 64) >> 7
index = raw < 0 ? -n : n  (mod 256)
```

This maps `-32768` through the unsigned magnitude 32768. All table bins,
nearest-bin boundaries, signed endpoints, and 10,000 seeded random angles are
covered by the transform regression suite.

`p3d_sincos_fine16` instead retains all 15 periodic angle bits. Between table
entries `i` and `i+1`, with fraction `f=0..127`, it rounds the complete signed
weighted numerator:

```text
round((table[i] * (128-f) + table[i+1] * f) / 128)
```

Exact halves round away from zero. Reflection into the positive half turn
makes sine odd and cosine even byte-for-byte. Exhaustive host analysis bounds
the component error at 3.095 signed-Q15 counts and direction error at
0.00220 degrees.

The generated include also contains fine atan nodes and two coarse
inverse-search tables:

- 65 first-octant `atan` words for ratios `0/64..64/64`;
- 32 exact first-octant `atan2` dot-product boundaries;
- 64 monotonic `asin` nearest-sine thresholds.

`p3d_atan2_16` returns the table direction with the greatest dot product.
Exact ties choose the numerically smaller signed phase, including the
`+127/-128` wrap boundary. `p3d_asin16` returns canonical pitch in
`-64..+64` table phases and chooses the smaller magnitude on a tie. Both
functions emit Pingo words that are exact multiples of 128.

`p3d_atan2_fine16` computes a rounded Q15 `min/max` ratio using a 15-step
low-word restoring division, then linearly interpolates the adjacent fine
atan nodes. It returns every raw Pingo angle bit in canonical
`-16384..16383` form. Its exhaustive first-octant arithmetic/table error is
at most 1.052 raw angle units, or 0.01156 degrees. The camera solver uses this
fine API; the coarse inverse APIs remain unchanged for matrix/object
compatibility.

The camera solver also contains a namespaced 24-bit integer square-root core
adapted from the established `sqrt24` implementation in `fixed168.inc`. It is
the deliberate exception to the logical-low-word register convention:
`p3d_lookat_isqrt24` consumes a genuine ADL `UHL:H:L` radicand and returns its
floor root in `UDE:D:E` plus the remainder in `UHL:H:L`. It is internal to the
look-at path. All public camera inputs and outputs remain 16-bit words.

## Transform contracts

Translation performs three signed low-16 additions. It commits all three
components only when every addition is representable; carry leaves the input
vector unchanged.

Axis rotations match Pingo's current matrices:

```text
X: y' = round((y*cos - z*sin) / 32767)
   z' = round((y*sin + z*cos) / 32767)

Y: x' = round((x*cos + z*sin) / 32767)
   z' = round((z*cos - x*sin) / 32767)

Z: x' = round((x*cos - y*sin) / 32767)
   y' = round((x*sin + y*cos) / 32767)
```

Each two-product numerator is accumulated at signed 32-bit width and narrowed
once. Axis routines are transactional: carry leaves all three components
unchanged. XYZ rotation applies X, then Y, then Z and restores the original
vector if any axis fails.

`p3d_mat3_mul_vec3_16` consumes an 18-byte row-major matrix whose coefficients
are restricted to `-32767..32767`. Each row accumulates three products at
signed 32-bit width and narrows once. Carry reports either accumulator or
result overflow and leaves the input vector unchanged.

`p3d_mat3_mul_mat3_16` applies the same three-product rule to every output
element. It calculates all nine results before committing, so exact
source/destination aliasing is supported and any failure leaves the left
matrix unchanged.

An orientation matrix maps object-local column vectors into world coordinates.
Pingo's absolute Euler convention is:

```text
R = Rz(z) * Ry(y) * Rx(x)
```

Intrinsic local rotations right-multiply the current orientation. The exact
fixed-point XYZ order is:

```text
((R * Rz(dz)) * Ry(dy)) * Rx(dx)
```

Each axis boundary narrows independently. This order is continuously
equivalent to `R*(Rz*Ry*Rx)` but explicitly specifies the integer rounding.

Orientation-matrix axis composition has one deliberate Q15 boundary rule.
Two rounded table directions that mathematically land on a cardinal can
produce a normalized coefficient of exactly `+32768` or `-32768`. Matrix rows
clamp only those one-count results to `+32767` or `-32767`; any larger result
still reports overflow. General scalar and vector rotations retain strict
signed-16 overflow behavior. This prevents a held local rotation from
transactionally retrying the same cardinal-boundary tick forever.

`p3d_mat3_to_euler16` exports canonical Pingo Euler words. Away from gimbal
lock:

```text
y = asin(-r20)
x = atan2(r21, r22)
z = atan2(r10, r00)
```

At either canonical quarter-turn pitch it chooses `z=0` and
`x=atan2(-r12,r11)`. `p3d_mat3_from_euler16` performs the inverse construction
using the same lookup table and fixed-point axis primitives.

Canonical Euler triples describe the same orientation but their individual
components are not continuous feedback signals. An equivalent branch can
change pitch or roll by roughly a half-turn while leaving the represented pose
unchanged. Physics, attitude indicators, and horizon code should derive the
needed quantities from `p3d_object_orientation` or
`p3d_camera_orientation`, not consume exported Euler components independently.

## Persistent object state

The eZ80 is authoritative because the Pingo command stream is write-only.
`p3d_object_size` is 64 bytes, with a named `equ` for every field:

| Offset | `equ` | Size | Meaning |
|---:|---|---:|---|
| 0 | `p3d_object_dirty` | 1 | Known and caller-owned dirty bits |
| 1 | `p3d_object_reserved` | 1 | Reserved, preserved by motion |
| 2 | `p3d_object_sid` | 2 | Pingo control/buffer ID |
| 4 | `p3d_object_oid` | 2 | Object ID |
| 6 | `p3d_object_mid` | 2 | Mesh ID used by object creation |
| 8 | `p3d_object_bmid` | 2 | Texture bitmap ID used by creation |
| 10 | `p3d_object_world_position` | 6 | Absolute Pingo translation vec3 |
| 16 | `p3d_object_pingo_rotation` | 6 | Absolute canonical Euler vec3 |
| 22 | `p3d_object_scale` | 6 | Absolute unsigned-8.8 scale vec3 |
| 28 | `p3d_object_orientation` | 18 | Row-major Q15 local-to-world matrix |
| 46 | `p3d_object_local_linear_velocity` | 6 | Local translation words/time unit |
| 52 | `p3d_object_local_angular_velocity` | 6 | Local angle words/time unit |
| 58 | `p3d_object_angular_residual` | 6 | Sub-table-bin angular residual |

The current Pingo create command consumes exactly `sid`, `oid`, `mid`, and
`bmid`; object/mesh texture-coordinate uploads do not introduce another
resource ID. The reserved byte leaves the word fields aligned and is available
for a future state flag without changing the offsets.

Known dirty bits are:

```text
position    0x01
rotation    0x02
scale       0x04
create      0x08
```

`p3d_object_init16` consumes an eight-byte `sid,oid,mid,bmid` tuple, overwrites
the complete state, selects identity pose/unit scale/zero velocities, and sets
all four known dirty bits for initial synchronization.

`p3d_object_translate_local16` transforms a caller-supplied local displacement
through the current orientation, adds the world result to the absolute
position, and marks position dirty only when the rounded position changes.
Thus conventional object-forward motion is a negative local-Z displacement.

Object-local rotation routines update the matrix intrinsically, export
canonical absolute Euler words, and rebuild the matrix from that export. The
rebuild removes accumulated Q15 orthogonality drift and keeps subsequent eZ80
movement aligned with the pose visible in Pingo. Rotation is marked dirty only
when the absolute exported Euler command changes; nonzero deltas that compose
to the same pose remain clean.

`p3d_object_step16` integrates one caller-defined time unit. It applies angular
velocity first and then transforms local linear velocity through the resulting
orientation. Angular lookup has 1/256-turn resolution, so each axis retains a
residual:

```text
total        = velocity + residual          (16-bit angular wrap)
new_residual = ((total + 64) mod 128) - 64
delta        = total - new_residual
```

This makes sub-bin rates accumulate instead of vanishing forever. The
ties-toward-positive rule keeps a stationary `-64` residual stable. A complete
64-byte stack snapshot makes the tick transactional: a later position overflow
also rolls back the earlier rotation, residual, and dirty changes.

## Optional sampled pose cycles

`3d_pose_cycle.inc` is a separate optional companion. It must be included only
once, after the core definitions. Its `p3d_object_apply_pose_sample8` routine
takes an object state in `IX`, the first pose record in `IY`, and a zero-based
record index in `A`. The caller must keep that index within the generated
table's actual 2..256-record extent; the loader deliberately performs no
boundary or consistency check.

Each `p3d_pose_sample_size` 24-byte record contains six bytes of fine absolute
Pingo wire Euler words followed by the matching 18-byte row-major Q15
local-to-world matrix. The loader installs both, ORs
`p3d_object_dirty_rotation` into the existing dirty byte, clears carry, and
preserves `BC`, `DE`, `HL`, `IX`, `IY`, and all shadow registers. Other object
state is unchanged.

`scripts/generate_pose_cycle.py` creates deterministic tables for 2..256
samples around a local X, Y, or Z axis. Keeping the wire Euler and internal
matrix side by side is intentional: the former uses 32,767 units per turn,
while the fast internal trigonometric domain uses a 32,768-unit binary turn.
Phase advancement, wrap, rate, direction, and pause behavior remain
application policy.

## Optional flight-simulator companion

`3d_fsim.inc` is a separate optional companion. Include it exactly once after
`3d.inc` and `3d_sincos_table.inc`. It depends on the core's matrix, vector,
inverse-trigonometric, object-offset, and Pingo command definitions, but it
does not depend on `3d_pose_cycle.inc`.

The companion is the caller-owned subset of the later F2 flight work. It owns
no flight state, key map, camera state, terrain state, packet buffer, or
transport. In particular it is not a complete flight model and none of its
packet builders executes `RST.LIL $18`.

### F2 scalar kernels

The F2 policy bounds are exposed as
`p3d_fsim_f2_rate_limit=512` and
`p3d_fsim_f2_velocity_limit_q8=8192`. They describe the qualified donor model,
not universal aircraft limits.

`p3d_fsim_f2_apply_axis_moment16` takes the current signed rate in `HL`, a
signed demand of exactly `-1`, `0`, or `+1` in `A`, and a positive moment in
`DE`. It first applies F2 damping, then subtracts, omits, or adds one moment
according to the demand sign, and clamps the result to `-512..+512`. The
qualified model supplies an already bounded rate and moments 8, 12, or 24.
Arbitrary operands that overflow the signed-16 moment addition are outside the
contract. The routine returns the new rate in `HL`, destroys `AF` and `BC`,
and preserves `DE`, `IX`, `IY`, and all shadow registers. Its return flags are
not a status result.

The four leaf kernels are:

| Routine | Input/output | Destruction and preservation |
|---|---|---|
| `p3d_fsim_f2_damp_rate16` | `HL` signed rate; decay by approximately 1/16 magnitude, with a minimum one-count decay to exact zero | destroys `AF`, `BC`, `DE`; preserves `IX`, `IY`, shadows |
| `p3d_fsim_f2_clamp_rate16` | clamp signed `HL` to `-512..+512` | destroys `AF`; preserves `BC`, `DE`, `IX`, `IY`, shadows |
| `p3d_fsim_f2_drag_from_velocity_q8_16` | `DE = -(DE >> 8)` for signed-Q8 velocity, using an arithmetic shift | destroys `AF`; preserves `BC`, `HL`, `IX`, `IY`, shadows |
| `p3d_fsim_f2_clamp_velocity_q8_16` | clamp signed-Q8 `HL` to `-8192..+8192` | destroys `AF`; preserves `BC`, `DE`, `IX`, `IY`, shadows |

### Matrix and point composition

`p3d_fsim_mat3_transpose16` copies the transpose of the row-major signed-Q15
matrix at `IY` to the 18-byte destination at `IX`. Source and destination must
be distinct and must not overlap; its qualified bytewise write order is not an
in-place transpose. It destroys only `AF` and preserves `BC`, `DE`, `HL`, both
index registers, and all shadow registers.

`p3d_fsim_local_point_to_world16` treats the writable six-byte vec3 at `IX` as
an object-local point and the `p3d_object` at `IY` as a retained local-to-world
pose. It computes:

```text
world point = object world position + object orientation * local point
```

Carry clear reports success. Matrix failure leaves the vec3 unchanged. If the
matrix succeeds but translation overflows, carry is set and the vec3 retains
the rotated local offset rather than the original input. A caller requiring an
immutable source must copy it to work storage first. The writable `IX` vec3
must not overlap the `p3d_object` at `IY`. The routine preserves `IX` and `IY`
and destroys both `AF` banks plus all general-purpose registers in both banks.

`p3d_fsim_mat3_horizon16` derives a branch-free coarse horizon attitude from
the row-major signed-Q15 matrix at `IX`:

```text
pitch = asin(-r1c2)
roll  = atan2(r1c0, r1c1)
```

It returns pitch in `HL`, roll in `DE`, and carry clear. Both angles are signed
Pingo words at the core inverse tables' 128-count granularity. Negating the
otherwise invalid Q15 value `-32768` saturates to `+32767` before `asin`.
`IX` and `IY` are preserved; both `AF` banks, `BC`, and all shadow
general-purpose registers are destroyed.

This helper is the reusable extraction step only. Viewport scale, horizon
placement, colors, polygon construction, and VDU drawing remain application
policy.

### Experimental Pingo packet builders

The companion exposes caller-owned builders for Pingo subcommands 51, 52, and
53. These protocol additions remain experimental. Merely packaging the
builders does not assert support in stock firmware or promote the commands to
a stable community contract.

Every builder takes the unsigned Pingo control/scene ID in `BC` and the packet
destination in `IY`. It returns `HL=IY`, the exact packet size in `BC`, and
carry clear. Each destroys `AF`, `BC`, and `HL`, preserves `DE`, `IX`, `IY`,
and all shadow registers, builds only the bytes shown below, and performs no
send:

| Builder | Additional input | Size | Packet after `23,0,0xA0,sid,0x49` |
|---|---|---:|---|
| `p3d_fsim_build_object_active16` | `DE=object ID`; `A=0` inactive or `1` active | 10 | `51, oid, active` |
| `p3d_fsim_build_object_xyz_translation24` | `DE=object ID`; `IX` points to exact signed-24 little-endian X, Y, Z | 18 | `52, oid, x[3], y[3], z[3]` |
| `p3d_fsim_build_projection_far16` | `DE=far distance in Pingo scene units` | 9 | `53, far` |

The source and destination of the command-52 builder must not overlap. Its
three-byte coordinates use the same raw translation-count unit as legacy
subcommand 17. The command-53 builder deliberately encodes all 16-bit values;
the experimental firmware accepts 2..65535 and consumes but rejects 0 and 1,
preserving its prior far setting.

Caller-owned construction is the public boundary because the donor clients
patched static packet bodies and immediately sent an unacknowledged VDU
stream. Keeping storage and transport at the integration layer makes these
routines reusable and reentrant with respect to packet state. It also avoids
inventing a camera-sync routine: the application-local camera senders found in
the flight fixtures duplicate earlier demo policy and remain outside this
companion under `P3D-API-1`.

The complete 77-byte, single-instance `flight-input.inc` state/model;
cockpit/chase toggle policy; fallback-backdrop renderer; terrain/LOD managers;
and P3DM/flat-pattern clients are genuinely new application modules, not
earlier-demo duplicates. They are deliberately deferred rather than presented
as this standalone API. Their exact lineage and known qualification boundaries
are recorded in `provenance.md` and `TODO.md`.

## Persistent camera state and aim-at-object

Pingo camera commands describe a world pose. The renderer performs the one
required inversion to turn that pose into a view matrix. The eZ80 therefore
retains camera state in the same world-coordinate sense as object state:

| Offset | `equ` | Size | Meaning |
|---:|---|---:|---|
| 0 | `p3d_camera_dirty` | 1 | Position/rotation dirty bits |
| 1 | `p3d_camera_look_flags` | 1 | Valid, pole, and inverted-frame state |
| 2 | `p3d_camera_sid` | 2 | Pingo scene/control ID |
| 4 | `p3d_camera_world_position` | 6 | Absolute camera translation vec3 |
| 10 | `p3d_camera_pingo_rotation` | 6 | Absolute emitted Euler vec3 |
| 16 | `p3d_camera_orientation` | 18 | Matching row-major Q15 matrix |
| 34 | `p3d_camera_pole_yaw` | 2 | Last reliable canonical pole-frame yaw |

`p3d_camera_size` is 36 bytes. `p3d_camera_init16` copies a scene ID and
position, establishes an identity pose, and marks position and rotation dirty.

`p3d_camera_aim_at_point16` takes the roll policy explicitly in `A` on every
call. `p3d_camera_aim_at_object16` is the corresponding wrapper whose target is
the object's retained `p3d_object_world_position`. Both preserve their IX/IY
pointers and leave the complete camera state unchanged when the target and
camera positions coincide or the policy is invalid.

For a mathematical direction `d = target - camera`, current Pingo pose
semantics require:

```text
pitch X = atan2(dy, sqrt(dx^2 + dz^2))
yaw   Y = atan2(-dx, -dz)
roll  Z = 0
```

The negative X term in yaw is significant. The old bearing diagnostic used
`atan2(+dx,-dz)` for firmware that treated a camera transform directly as a
view matrix; that convention is stale now that Pingo correctly inverts a
camera world pose once.

Subtracting two signed position words can produce a 17-bit difference. The
solver avoids low-word wrap by converting each signed endpoint to monotonic
offset-binary form, then retaining the sign and unsigned 0..65535 magnitude.
For pitch, pole classification, and the horizontal root, all three magnitudes
receive common shifts until the largest is in `1024..2047`. This keeps about
eleven direction bits while guaranteeing:

```text
dx^2 + dz^2 < 2^23
```

The horizontal square root is rounded to nearest before the fine inverse
lookup. Yaw uses the exact X/Z magnitude pair independently; only endpoint
differences above 32767 require one common right shift. A dominant vertical
component therefore cannot erase horizontal yaw precision just outside the
pole cone.

Looking parallel to world up does not determine a horizontal camera frame.
The state therefore enters a pole cone when:

```text
horizontal <= |dy| / 32
```

and leaves only when:

```text
horizontal > |dy| / 16
```

Inside that hysteresis band it retains the last reliable canonical yaw and
uses an exact +/-90-degree pitch. The wider exit cone prevents frame chatter
when a quantized or noisy target sits near the boundary.

A single coarse simulation step can leap across both sides of that narrow
cone. Away from the held-pole state, continuous mode therefore calculates
both equivalent Euler representations and selects the smaller sum of wrapped
pitch and yaw changes from the previously emitted pair. Each component uses
the shortest distance in the library's 32768-word turn, and the two distances
have an unsigned sum no greater than 32768. An exact tie retains the prior
branch. This keeps a pole traversal continuous without imposing a simulation
sampling-rate precondition, while an ordinary large yaw change near the
horizon still selects the upright representation when it is the shorter full
Euler path.

The required roll policies are:

- `p3d_camera_roll_upright`: always select the world-up Euler branch. Passing
  over a pole changes canonical yaw by approximately 180 degrees so the camera
  emerges upright.
- `p3d_camera_roll_continuous`: retain the prior horizontal frame through the
  pole and select the exact equivalent inverted Euler branch on the far side.
  Pitch consequently continues through +/-90 degrees and the camera emerges
  on its back instead of twisting its horizon upright.

The equivalent branch is exact in the library's 32768-word binary turn:

```text
if pitch >= 0: inverted_pitch = +180 degrees - pitch
else:          inverted_pitch = -180 degrees - pitch
inverted_yaw = canonical_yaw + 180 degrees
```

At a raw half-turn tie, the prior pitch sign is retained. Pingo's float bridge
uses `2*pi/32767` while the integer library uses a 32768-word binary turn, so
that conversion contributes at most about 0.0055 degrees of matrix/wire
difference. Euler Z remains zero; for general orientations that world-last Z
stage is not itself a local camera roll. A future API for an explicit
arbitrary local roll should rotate the camera basis/matrix and then export the
result.

Both aim routines build `p3d_camera_orientation` directly from interpolated
fine sine/cosine and the selected zero-roll Euler representation. They do not
pass it through `p3d_mat3_to_euler16`, because that routine intentionally
canonicalizes away the continuous over-pole branch. Rotation dirty is set
only when the emitted Euler bytes change. A complete camera snapshot makes
flags, pole memory, Euler words, and matrix construction transactional.

## Pingo synchronization

The current buffered-command selector is `0x49`. The state uses existing
absolute object subcommands:

| Dirty bit | Subcommand | Packet bytes after object ID |
|---|---:|---|
| create | 5 | mesh ID, texture bitmap ID |
| scale | 9 | X, Y, Z unsigned-8.8 words |
| rotation | 13 | X, Y, Z absolute Pingo angles |
| position | 17 | X, Y, Z absolute translation words |

`p3d_object_build_create16` and `p3d_object_build_next_dirty16` construct the
13- or 15-byte VDU packet in caller-owned scratch memory.
`p3d_object_sync16` repeatedly sends the next packet through `RST.LIL $18` and
clears each known bit after the call returns. The byte-stream API has no
delivery-status result, so synchronization cannot report a VDP-side rejection.
Unknown high dirty bits are retained.

There is currently no `p3d_camera_build_next_dirty16` or
`p3d_camera_sync16`. Camera-state consumers own that transport boundary. The
historical 2026-07-30 development log named `p3d_camera_sync16` among the
intended additions, but no such symbol was implemented or regression-tested;
the publication decision is tracked as `P3D-API-1` in `TODO.md`.

The axis and matrix routines deliberately use a small number of balanced stack
operations to retain in-place transactional behavior while the GP shadow bank
holds full-width products. IX and IY are preserved.

## Shadow-register and interrupt contract

Routines document both active- and shadow-bank destruction explicitly.
Code using `exx` or `ex af,af'` assumes any enabled interrupt handler preserves
the register banks it uses. If an application has a different interrupt
contract, it must protect the call at that integration boundary rather than
adding stack traffic to every arithmetic primitive.

## Validation status

The established routines pass two deterministic suites under the current
Pingo-compatible Fab profile:

- 60,596 scalar arithmetic records;
- 71,834 trigonometric and transform records.

Both suites contain at least 10,000 seeded random records per public operation
plus directed endpoints, rounding boundaries, cardinal rotations, signed
overflow, atomic-failure, dense matrix, and accumulator-overflow cases. PRT1
timing excludes file I/O and includes the same operand setup, comparison, and
loop bookkeeping convention used by the original AgonMaths fixtures.
The transform harness also verifies IX/IY preservation on every vector
operation, full 24-bit shadow-GP preservation where promised, and that no
operation writes into its 18-byte auxiliary input field.

The correctness-loop timing is useful for regression comparisons, but it is
not a full-success frame budget: its random workload includes operations that
take an early overflow exit. After a clean transform run, the harness therefore
performs a second, file-free benchmark of 20,000 guaranteed-success calls per
entry point. It uses invariant half-turn rotations and identity-like matrix
fixtures, measures matching empty loops, and subtracts the loop, `DI`/`EI`, and
angle-load baseline. The resulting times retain API `CALL`/`RET` and the entire
successful arithmetic path. Each raw interval is uninterrupted, leaving only
the PRT's sub-millisecond quantization and the corresponding baseline-
subtraction uncertainty.

The 251,337-record pose suite independently covers coarse and fine inverse
trig, fine sine/cosine, matrix multiplication, Euler import/export and gimbal
handling, intrinsic
matrix/object rotation, local object translation, initialization, angular
residuals, whole-tick rollback, ID/scale/velocity preservation, unknown dirty
bits, camera initialization, full signed-endpoint aiming, both pole policies,
pole hysteresis and skipped crossings, packet bytes/priority/return registers,
and pointer/input immutability. It includes 16,384 consecutive held-control
ticks spanning both directions of every local axis and two mixed-axis paths;
the historical pure-pitch failure at tick 807 is crossed repeatedly. Every
public arithmetic, object pose, camera pose, or packet-builder entry point has
at least 10,000 deterministic cases. The suite uses 224-byte records and
pauses PRT1 around every batch read.
`p3d_object_sync16` itself is excluded because it crosses the live,
unacknowledged VDU stream boundary.

The optional `3d_fsim.inc` has a separate 912,001-record, correctness-only
real-eZ80 suite. The five F2 groups exhaust all signed-16 inputs; axis-moment
application covers every input word with all three demands and qualified
moments 8, 12, and 24. Transpose, local-point-to-world, matrix horizon, and
each command-51–53 builder have directed boundaries plus at least 10,000
seeded cases; all command-51 cases use the documented active values `0` or
`1`. The harness verifies documented values and carry, both
local-point failure stages, full-width active/index and shadow-register
contracts, source/object immutability, surrounding work-area canaries, and
exact builder return pointers and lengths. All 912,001 records pass with zero
errors.

That suite qualifies the builders' bytes and ABI only. It does not send a
packet, prove stock-firmware support, or close the command-51–53 promotion gate
`P3D-API-2`. The companion also contains no throttle, aero, runway, full-model
step, or ADL24 position integrator, so its result does not qualify those
explicitly deferred application-global behaviors.

`scripts/test_camera_smoothness.py` adds deterministic level/elevated fly-bys
at several distances, velocities, and render-sampling strides. It checks
monotonic full-word yaw, bounded angle and step error, the signed half-turn
seam, scaled-trajectory invariance, and the near-pole independent-X/Z case.

Hardware execution remains a separate validation gate.
